### TRACK B (secondary) -- camera image quality, via the 3A stack

Framing this correctly matters more than the work itself.

The green cast is **not** a calibration-table problem to be hand-tuned. The
ISP's 3A is split between the kernel and a **userspace algorithm daemon** that
talks to the driver over the sbuf shared-buffer channel. The kernel side
collects statistics and publishes them; userspace is supposed to compute the
result and hand it back. Concretely, `ae_set_new_param()` is the only caller of
`fsm_raise_event( event_id_ae_result_ready )`, which is the only thing
`AE_fsm_process_event()` handles, which is what eventually programs the sensor.
With no daemon, that loop is open:

```
ISP kernel driver     OK
IQ tables             present, unverified
statistics generation OK
userspace 3A daemon   MISSING
                      -> AWB never updates, AE partial, AF absent
```

So the task is **not** "fix the green tint". It is:

> Find the original Khadas/Amlogic userspace 3A stack and establish exactly
> which AE/AWB/AF functionality depends on it. Do not hand-tune calibration
> until that is understood.

Apply the standing rule: Khadas Ubuntu 5.15 produced a good image, so the full
chain existed. Find it in the old BSP/userspace, then port or replace it
deliberately. Do not invent an AWB algorithm.

Do not block Track A on any of this.

## RESOLVED, 2026-09-15 — DS1 1920x1080 captures real frames

DS1 at 1920x1080 works, repeatably, and the frames contain a real image:
`docs/images/ds1-1920x1080-first-capture.png`.

Verification, all on a module built from `19a82a0`, with the
`stream_rearm_any` parameter gone:

```
DS1 run 2: 4 frames    DS1 run 4: 4 frames    DS1 after FR: 4 frames
```

Image content of the dumped frame, against the handover's own benchmark
(0.986 row correlation for a known-good FR capture, "no stride above 0.53"
for the garbage case):

| Measure | Value |
| --- | --- |
| Row-to-row correlation | **0.9894** |
| Column-to-column correlation | 0.9813 |
| Rows 100 apart | 0.3870 |
| Shuffled-pixel baseline | 0.0007 |
| Distinct Y values | 249 |

Plane sizes are exactly 2073600 + 1036800 = NV12 1920x1080, and the picture
shows no shear or stride artefact.

### The three bugs, in the order they were peeled

1. **Temper left in the datapath doing DMA against address 0** (`7e5c6ff`).
   `sensor_configure_buffers()` bypasses Temper for want of buffers, then
   `acamera_init_context_seq()` loads `settings_context_top`, whose
   `{ 0x18eb8, 0x0L, 0x7, 1 }` entry puts it straight back. Its MSB DMA
   channels default to 1 and every bank base is 0. FR escaped only because its
   S_FMT re-runs `sensor_configure_buffers()` afterwards. **This was the hard
   hang at `imx415 streaming on`.** Fixed by preserving the bypass bit across
   the sequence load.

2. **The CSI-2 receive path was never brought back up** (`e3840f7`).
   `stop_streaming()` calls `am_adap_deinit()`/`am_mipi_deinit()`, but the
   bring-up sat in `sensor_set_mode()`, which only a preset change reaches.
   DS1 selects no preset, so the sensor was started into a deinitialised
   receiver. Khadas `IMX415_drv.c` calls `sensor_set_iface()` from
   `start_streaming()` and has it commented out in `sensor_set_mode()`; we now
   match. **This was the silent 0-frame case.**

3. **The ISP was quiesced but never re-armed** (`19a82a0`).
   `quiesce` ran for the last stream of any type; `rearm` was gated to FR by
   the `stream_rearm_any` parameter. So DS1 masked the ISP on the way out and
   never unmasked it on the way back in: the first DS1 run after a module load
   worked and every later one returned 0 frames. Parameter dropped, rearm now
   mirrors the quiesce test.

Earlier conclusions that turned out to be wrong, recorded so they are not
re-derived: the DS1 DMA writer was never the thing hanging the board
(`ds1_dma_hold` proved it, `800d72f`), and the downscaler was configured
correctly all along once `e1731d1` restored the missing
`crop_resolution_changed()` call.

### Known, out of scope for this task

The image has a green cast — AWB gains sit at defaults because the ISP's 3A
loop needs the userspace algorithm daemon over sbuf. **This is pipeline-wide,
not DS1-specific**: a same-scene FR capture measures U/V 110.9/111.8 against
DS1's 119.2/120.3, both well below neutral 128, with Y means 29.0 and 29.4.
Worth its own task.

Still open from earlier sections: the `LOG_CRIT` trace in `crop_func.c` is
temporary and wants restoring to `LOG_NOTICE` before shipping, and
`ds1_dma_hold` (`800d72f`) is a bring-up diagnostic that can go once DS1 is
settled. The reference clone at `external/khadas-common_drivers/` is still
untracked, and the test tools now live in `platform/camera/tools/`, not the

### The DS1 DMA writer is not what hangs the board

`ds1_dma_hold=1` (commit `800d72f`) runs the entire DS1 path — S_FMT, REQBUF,
QBUF, STREAMON, sensor on — with valid buffers armed but both DS1 writer
enables forced to zero, in the arm path and the per-frame path alike.

Result, under marker `DS1_HOLD_LOAD_20260915`: **the board hung at exactly the
same point**, the last line being `imx415 streaming on`, with the writers
provably disabled (`TRACE DS1 DMA HELD: Y address=0xe7700000
UV address=0xe7900000; both writer enables remain zero`).

Therefore **retire the memory-corruption theory for this hang.** The DS1
writer cannot be scribbling over kernel memory when it is switched off. The
crashes described in §3(b) were real, but they belong to the pre-`434dacd`
stride bug; they are not what the board does today.

### Root cause found: Temper is left in the datapath with DMA against address 0

This is verified by code and by the logs, but is **not yet confirmed on
hardware** — see "Board state" below.

At module load the order is, and the UART timestamps confirm it (160.889 then
161.259):

1. `sensor_configure_buffers()` finds no temper buffers and sets
   `top_bypass_temper = 1`, logging "Temper is disabled".
2. `acamera_init_context_seq()` loads `settings_context_top`, which contains
   `{ 0x18eb8, 0x0L, 0x7, 1 }` — clearing bits 0..2, putting sinter, **temper**
   and ca_correction back into the datapath.

Nothing restores it afterwards, and what is left behind does DMA:

- `temper_enable` (`0x1aa1c`) is not in the sequence and stays 0 — but
  `temper_enable` only stops the block doing temporal work; `top_bypass` is
  what removes it from the datapath.
- the MSB DMA reader and writer (`0x1ab78` onwards) **default to 1** and
  nothing clears them; `isp_temper_disable_msb_dma` is off by default.
- every temper bank base address is 0.

A temper DMA reader and writer armed against physical address 0 matches the
symptom exactly: a hard hang at sensor start, no oops, no backtrace.

**Why FR works is an accident.** FR's S_FMT calls
`fw_intf_stream_set_resolution()`, which selects a sensor preset and re-runs
`sensor_configure_buffers()` — after the context sequence — restoring the
bypass. A DS1-only S_FMT sets no preset (correctly: DS1 does not drive sensor
resolution), so it never runs again and the sensor starts with temper live.
This is the one configuration difference between the path that works and the
path that does not.

Reference note, per `AGENTS.md`: the Khadas reference has **no**
`top_bypass_temper` write in `sensor_func.c` at all — the port added it — and
it carries a commented-out `acamera_isp_top_bypass_temper_write(..., 1)` at
the end of its own `acamera_init_context()`. The vendor evidently hit the same
edge and left a stub behind. Our fix restores the sensor's decision rather
than hardcoding a value, so it stays correct if temper buffers are ever
provided.

The fix (`7e5c6ff`) reads the bypass bit before `acamera_load_sw_sequence()`
and writes it back after. Only that one bit is restored; the rest of
`settings_context_top` is static structural configuration no FSM writes.

## 3. Where the work stands

FR (3864x2192) capture works and produces real images. The task is DS1 at
1920x1080, which the product needs — full-res for detection and streaming
wastes memory bandwidth.

### The bug chain, in the order it was peeled

**(a) FIXED and committed — the DMA writer stride was never programmed.**
Two halves of one omission:

- `isp-vb2.c: isp_vb_to_tframe()` never set `line_offset`. Khadas fills both
  planes from the negotiated `bytesperline` (`isp-vb2.c:154,159` in
  `isp_vb_mmap_cvt()`). Ours set only address and size, so every tframe reached
  the firmware with stride 0.
- `dma_writer.c: dma_writer_write_frame_queue()`'s enable block dropped the two
  stride writes the reference does there (`dma_writer.c:293` primary, `:299`
  UV). The surviving `line_offset_write()` calls are in the per-frame path in
  `dma_writer_pipe_update()` — one frame too late.

The unprogrammed DS1 stride defaults to `ACAMERA_ISP_DS1_DMA_WRITER_LINE_OFFSET_DEFAULT`
= **0x1000 = 4096**, so the first frame wrote 4096 * 1080 = 4.42 MB into a
2.07 MB buffer. Commit `434dacd`. Verified on FR: stride now arrives as 3968
where it was 0.

**(b) SUPERSEDED — see "Continuation 2" at the top.** The downscaler *is*
configured; `e1731d1` fixed that, and the hardware register dump proves it.
The crash analysis below is accurate for the pre-`434dacd` stride bug but is
**not** what the board does today. Kept for the reasoning, not the conclusion.

This was the live problem. Evidence, from a deliberately safe run (FR streaming,
DS1 S_FMT'd to 1920x1080 but never REQBUF'd/QBUF'd, so its DMA writer is never
armed):

- **No `TRACE DS update` line appeared at all.** That trace is in
  `crop_func.c: _update_ds()`, the only place that writes
  `acamera_isp_ds1_scaler_owidth/oheight`, the `hfilt_tinc`/`vfilt_tinc`
  ratios, and `acamera_isp_top_bypass_ds1_scaler`. It never ran.

If `_update_ds()` never runs, the scaler stays bypassed and the ISP keeps
emitting 3864x2192 lines into a DMA writer told to expect 1920x1080. The writer
runs past `active_height`: 1920 * 2192 = 4.2 MB into a 2.07 MB buffer, ~2.1 MB
of kernel memory overwritten.

That is consistent with every crash observed, and in particular with two
details that rule out an ordinary driver pointer bug:

- the `Modules linked in:` line is itself corrupted — truncated to one entry in
  one crash, degenerating into UTF-8 garbage mid-list in another. Module names
  are ordinary kernel memory and had already been overwritten before the oops
  handler ran.
- a `usercopy: Kernel memory exposure attempt detected from SLUB object
  'kmalloc-2k' (offset 0, size 93)` BUG on an unrelated object.

This is hardware scribbling over the kernel, not code dereferencing junk.

### Corrections to earlier conclusions — do not re-derive these

- `docs/ds1-scaler-analysis.md` says the stride omission explains the crash. It
  explains the **original** crash. It is necessary but **not sufficient**;
  something still overruns with the stride correct. That file is accurate about
  the mechanism it describes and about the reference comparison, but its "Root
  cause found" heading overstates the case. Read it together with this page.
- `acamera_fw_stream_rearm()` is **not** the trigger. A DS1 run once survived
  and was misread as proof that rearm was the difference; in fact it survived
  because the preceding FR `STREAMOFF` had quiesced the ISP. From a fresh module

- "negotiated size == ISP pipe size == DMA buffer size" was wrong. Three of the

- The single-context flattening hypothesis (upstream threads `ctx_id`, this
  port removed it) is not needed to explain anything seen so far. Park it.

## 5. Safety rule, learned the hard way

**Do not run a DS1 streaming test without UART capture already running.**
Four attempts hard-hung the board and cost four resets; three of them produced
no usable evidence because the board dies faster than ssh or `dmesg` can report.

Prefer the safe tool first. `platform/camera/tools/frds1.c` streams FR (known good) with DS1
formatted but never queued: the DS1 writer is never armed, so it cannot write
anywhere, yet the ISP is running and the scaler configuration is live and
observable. It answers the scaler question at zero risk.

Also note `platform/camera/tools/ds1arm.c` cannot observe DMA arming at all — vb2 only hands
queued buffers to the driver inside `vb2_start_streaming()`, so
`dma_writer_write_frame_queue()` is not reached until STREAMON.

## 8. Logging

`SYSTEM_LOG_LEVEL` is `LOG_ERR` (`inc/sys/system_log.h`), and `FW_LOG_LEVEL` is
`LOG_NOTHING`. Only `LOG_ERR` and `LOG_CRIT` reach the kernel log. To see an
existing `LOG_INFO`/`LOG_DEBUG`/`LOG_NOTICE` line, temporarily raise it to
`LOG_CRIT` rather than hunting for a runtime knob.

## 9. Register accessors — a trap worth knowing

There are two register banks and they behave differently:

- `inc/isp/acamera_isp_config.h` — `system_hw_*`, writes hardware directly, and
  **ignores** the `base` argument in favour of the single ioremap in
  `system_hw_io.c`.
- `inc/isp/acamera_isp1_config.h` — `system_sw_*`, writes a **software config
  shadow** that only reaches the ISP when the page is DMA'd across at the next
  frame start, and **dereferences `base + offset` directly**, so a wrong base is
  an oops rather than a no-op.

All the `acamera_isp_{fr,ds1}_dma_writer_*` accessors are the second kind. So
"we wrote the geometry" and "the hardware has the geometry" are different
claims, and reading back through the same accessor confirms only the former.
